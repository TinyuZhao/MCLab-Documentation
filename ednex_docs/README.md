# Ednex / MC4 Documentation

This is the standalone Ednex / MC4 MicroPython documentation tree. Its layout
follows the MCLab documentation without being mixed into the repository's
existing `docs/` MicroPython documentation.

## Directory layout

Documentation sources live in `source/` and are grouped by product area. The
API snapshot under `source/_api_stubs/` is the public build input; it contains
signatures and documentation strings, not firmware implementation, and is
generated by `tools/generate_api_stubs.py` rather than checked in.

- `MCLab/`: APIs provided by the public `MCLab` Python package;
- `module/`: module drivers;
- `unit/`: sensors and peripherals;
- `event/`, `ui/`, and `hardware/`: MCLab event, display, and board hardware blocks;
- `generic/`: MCLab language and data blocks;
- `advanced/`: BLE, AI, and advanced features;
- `ezdata/`: EzData and Remote blocks;
- `iot_cloud/`: IoT cloud blocks;
- `mccloud/`: MC Cloud blocks;
- `blockly_custom/`: custom Blockly blocks;
- `contribute/`: contribution guide and page template;
- `refs/`: per-module substitution files included by the pages;
- `static/`: images and other static assets.

MCLab projects and MicroPython examples referenced by these pages live under
the repository-level `examples/ednex/` directory.

The private firmware tree generates that snapshot with the API extractor. The
public documentation tree does not import or require the firmware source.

## Build

Install Sphinx and the RTD theme:

```console
python3 -m pip install -r ednex_docs/requirements.txt
```

Run this from the repository root:

```console
make -C ednex_docs en
```

When working in the firmware repository, regenerate the public API snapshot
after changing a documented module:

```console
make -C ednex_docs api-stubs
make -C ednex_docs check-api-stubs
```

The generation command also removes obsolete Python files from the generated
API snapshot. Check mode reports the same stale files without modifying them.

The generated site is written to `ednex_docs/build/html/en/index.html`.

To run a strict build with warnings treated as errors:

```console
sphinx-build -W -b html ednex_docs/source ednex_docs/build/html/en
```

`source/conf.py` keeps hardware-only imports mocked for examples, but the
documentation build itself reads only the generated API snapshot and never
accesses a physical device or private firmware source.

## Continuous integration

`.gitlab-ci.yml` at the repository root builds and publishes this tree on
`gitlab.m5stack.com`:

- `build:docs` runs `make -C ednex_docs api-stubs` and then
  `make -C ednex_docs en` (strict, warnings are errors) and keeps the HTML as
  an artifact;
- `test:docs` runs `tools/test_generate_api_stubs.py` and
  `tools/test_driver_api_docs.py` (the latter is non-blocking while the
  `urequests.Response.json` docstring is missing);
- `pages` copies `ednex_docs/build/html/en` into `public/` and is only created
  for the `Project/Ednex` branch (or the default branch).

`source/_api_stubs/` is generated, so it is never committed; the pipeline
regenerates it before every build.
